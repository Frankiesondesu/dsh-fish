# 自建网页对话通道 —— 调研报告（2026-11-12）

> 背景：腾讯正在收紧对第三方 QQ 协议实现（LLOneBot / NapCat 一类）的打击，
> 我们的 QQ 通路正建立在这类实现上。本文调研：用**自建网页**实现与她的对话，
> 复用现有桥的哪些部分、对原项目的修改能压到多小。
> 本目录独立于 bridge/ 与 dsh-fish/，只放调研与（未来的）新通道代码。

## 0. 一句话结论

**工程量不大：一个 ~400 行的独立小服务，半天到一天能上线；桥和插件一行都不用改。**
更准确地说——桥里真正值钱的两层（递话通路 + 账本推送层）都可以原样复用，
需要新建的只是「网页外壳」；桥的 QQ 协议外壳（OneBot ws）反而是网页通道用不到的部分。

## 1. 现状链路（代码事实，2026-11-12）

```
入站（他 → 她）：
  QQ消息 → LuckyLillia(PMHQ+LLOneBot) --OneBot11 ws-reverse--> bridge.mjs(:6199/ws)
        → POST /dsh-fish/local/say {text, image?} + x-fish-key → DSH → 她

出站（她 → 各处）：
  her_say 工具 → 账本 events.jsonl（utterance + 「（她说）/（她主动说）/（陪你看）」前缀标记）
        → push.mjs 增量盯账本（字节 offset 落盘）→ deliver() → QQ
```

关键接口盘点（都在，都是现成的）：

| 件 | 位置 | 对网页通道的意义 |
|---|---|---|
| `POST /dsh-fish/local/say` | dsh-fish `lib/observe.js` handleSay（`/say` 界面用、`/local/say` 网关用共用） | 网页入站直接 POST 它，**不经过桥**；支持 `text` + `image`(base64，自动落盘后递路径让她 read_image)，且 `scene/channel/speaker/room/title/guest` **原样透传**（归一兜底在 say.js） |
| `POST /dsh-fish/local/steer` | observe.js handleSteer | 她没跑完时插话（网页端"再补充一句"用） |
| `POST /dsh-fish/local/wake` | observe.js（7788 查看器已在用） | 网页端"叫醒她"按钮可直接复用 |
| `createPusher({ …, deliver })` | bridge `push.mjs` | **deliver 是注入的回调** `(item)=>Promise`，监账本→推送的骨架（增量读/半行保护/失败不推进 offset/过期丢弃）全是现成的，换一个 deliver 就是网页推送 |
| 端口发现 + `x-fish-key` | bridge.mjs `discoverPort()`（netstat + /local/ping 认端口） | ~50 行，复制进新服务即可（DSH 重启端口会变，这段必须要有） |
| 密码访问模式 | viewer 7788（局域网要密码/本机免密） | 网页鉴权照抄这个口径 |
| 账本历史 | `~/.dsh-fish/events.jsonl`；查看器 `/api/data` 已翻成页面 | 网页的历史回放直接读同一份账本 |

**谁依赖腾讯：只有桥的 QQ 侧（LLOneBot 那条 ws 连接）。**
DSH、插件、账本、her_say 口径、查看器、push 的监账本骨架——全都不依赖。
所以"QQ 通道被打死"只会断掉图中两根 QQ 线，其余世界完好。

## 2. 方案对比

| 方案 | 改动面 | 能力 | 评价 |
|---|---|---|---|
| **A. 桥内加 web 端点** | 改 bridge.mjs（端口/路由/静态页/会话全塞进去） | 同 B | 桥已经 1362 行，QQ 协议与网页协议耦合后，QQ 侧出事会连累网页；不推荐 |
| **B. 独立 webchat 小服务**（新文件夹/新进程/新端口） | **bridge 0 行、插件 0 行、DSH 0 行** | 文字对话、图片、历史、多端 | ★ 推荐：新增不修改，进程隔离，QQ 挂了它不受影响 |
| C. 查看器加聊天页 | 改 viewer | 同 B | 破坏查看器"只读观测"的定位，聊天与观测混在一个服务里；不推荐 |
| D. 官方 QQ 机器人（上游 dsh-im-gateway 那条路） | 接入即可用 | 存续有保障，但私聊/群/主动消息限制多、要审核，且仍是腾讯地盘 | 当 QQ 通道真死的备选，不是本次目标 |
| E. 其他 IM（企微等） | 新桥接 | —— | 超出本次范围，记一笔不展开 |

## 3. 推荐方案 B 的设计

```
浏览器（PC/手机） ←HTTP+WS→ webchat.mjs（新，独立端口，如 :6210）
   ├─ 入站：网页发言 → POST /dsh-fish/local/say（channel:'web'，带 x-fish-key）
   │         ——与 QQ 入站共用 handleSay，DSH/她那边机制不变
   ├─ 出站：createPusher 复用（import 自 ../bridge/push.mjs）
   │         deliver = WS 广播给连着的浏览器；state 文件独立（push-state-web.json）
   └─ 历史：读 ~/.dsh-fish/events.jsonl（或查看器 /api/data）回放
```

### 3.1 路由口径（唯一需要拍板的设计点）

- **广播式（建议先用这个）**：她说的话（her_say）同时出现在 QQ 和网页——
  「说话就是说了，两扇门都听得见」。这完全符合 2026-11-07 定的 her_say 口径
  （唯一发送通路、不区分渠道），**零路由逻辑、零改动**。网页会话里她的回复
  也会推到 QQ——如果觉得吵，再演进到下面这种。
- 会话隔离式：网页发起的会话只回网页。技术上可行（her_say 事件带 sessionId，
  webchat 记住自己发起的会话 id 做过滤即可，也可不动插件），但多一套映射要维护，
  且「她的话分渠道藏」和现有口径有张力。**先不做，有真实需求再上。**

### 3.2 必须如实对她的部分（fork.13 / 养不塑对照）

- 网页入站消息带 `channel:'web'` 递给她——她看到的"这句话从哪来"必须是真的。
  say.js 本来就做渠道归一与兜底；`channel:'web'` 是否被兜底优雅接住需要一次实测：
  **如果**兜底不认，这是一处 ~5 行的插件小改（加一个渠道名 + 一句事实描述），
  是本方案唯一的"可能要动插件"点。
- 网页只是新增一扇门：不改变她开不开口、看什么、说什么（养不塑）；
  她的工具说明书不用改（her_say 口径不变），但若实测后她在网页会话里需要知道
  "对面是谁"，按事实层补一句说明书即可。

### 3.3 分期

| 期 | 内容 | 量 |
|---|---|---|
| MVP | 文字对话（网页→/local/say，账本→网页）、密码鉴权、历史回放、 steer 插话、wake 按钮 | ~400 行新代码，0 改原项目，**半天～一天** |
| 二期 | 图片展示（her_draw 产物直接 <img>，比 QQ 还方便）、网页传图（base64 已支持，套个上传控件）、语音（asr.mjs 复用 + 浏览器麦克风）、手机浏览器访问 | 每项 1~2 小时 |
| 三期 | 会话隔离（若拍板要）、公网可达（内网穿透——要先想清暴露面） | 视需求 |

## 4. 回答三个问题

1. **迁移工程大不大？** 不大。MVP 一个独立文件 ~400 行（含页面），半天到一天。
   数据零迁移——账本、身份、记忆全在原地，网页只是新门。
2. **能不能复用桥？** 能，且比预期更好：入站复用桥通往她的递话通路
   （/local/say，桥和网页是平级的两个网关），出站复用桥的账本推送层
   （push.mjs 的 deliver 本来就是注入式设计）。桥的 QQ 协议外壳一行不用动、
   也不用经过——"转接到网页"不是让流量改道，而是把桥里验证过的内核接出来。
3. **怎么最小化修改？** 新建不修改：webchat 独立文件夹独立进程，
   bridge.mjs / 插件 / DSH 零行改动（唯一例外是 3.2 的 channel 兜底实测，
   可能 5 行）。启停挂接走现有模式（start.cmd / 管理器 / fish-start.sh），
   无人值守时它和桥一样是常驻 node 进程，没有腾讯依赖，QQ 通道死了它照跑。

## 5. 风险与开放问题

- **暴露面**：webchat 默认只绑 127.0.0.1；局域网访问要密码（viewer 模式）；
  公网可达（内网穿透）放在三期，真要做要先过一遍"谁能跟她说上话"的门槛设计
  （ownerIds 白名单的网页版）。
- **匿名/陌生人**：网页没有 QQ 好友关系兜着，鉴权就是唯一的门——密码强度、
  会话过期、失败锁定，MVP 至少做密码 + 只绑本机/局域网。
- **账本只增不改**：网页消息同样入账本（和 QQ 一致），一年几 MB 的量级不变，
  push 层的增量读设计已经消化了这个。
- **她的接受度**：多一扇门=多一种被搭话的方式。开关（网页通道启停）放在用户
  手里，不放在她手里——这与现有 QQ 桥的权限结构一致。

## 6. 决策记录（2026-11-12 用户拍板，已实现）

1. 路由口径：**广播式**（她的话 QQ 和网页都出现，零路由逻辑）。
2. MVP 范围：**纯文字先跑**（MVP=最小可用版本；图片/语音放二期）。
3. 代码位置：**`webchat/`（bridge 旁）**，已实现并测试——见 `../webchat/README.md`。
